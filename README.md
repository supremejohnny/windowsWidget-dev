# Window Pet

Private development repository: [supremejohnny/windowsWidget-dev](https://github.com/supremejohnny/windowsWidget-dev). Public binary releases: [supremejohnny/windowWidget](https://github.com/supremejohnny/windowWidget). Source and development history must remain private; public release files are managed separately in `dist/public-repo/`. See [publishing boundaries](docs/PUBLISHING.md).

**0.0.1** — Windows binary release. Original source remains local. See [architecture](docs/ARCHITECTURE.md), [Windows/macOS compatibility and resource study](docs/COMPATIBILITY.md), and [release notes](docs/RELEASE_0.0.1.md).

A small Windows overlay pet attached to a selected corner of a window. Move the target window to swing the pet; click the pet to poke it. Click the single fixed anchor to tuck the pet away, leaving an 18 px static rope stub. Click again to bring the pet back.

## Build and run

```powershell
.\build.ps1
.\WindowPet.exe
```

This uses the C# compiler included with .NET Framework. No SDK or package download is needed on a standard Windows installation. Choose an open window, one of three placeholder pets or the `amiya_test1` image asset, one of four corners (upper left, upper right, lower left, lower right), and a fixed rope length: short 55 px, medium 85 px, long 130 px, or extra long 190 px. Press **Attach**. Use **Refresh** to update the window list and **Detach** to remove the pet. Closing the control window exits.
Close a running WindowPet before rebuilding its executable.

The built-in image and upstream license are embedded in the EXE. You can copy just the executable to another folder. **About** shows the version and third-party notices. The current application uses the system .NET Framework; it is not a self-contained runtime bundle or a macOS application.

To build a release candidate without disturbing a running project executable:

```powershell
.\build-release.ps1
```

The executable and SHA-256 checksum are written to `dist/v0.0.1/`. This also checks resource loading in a folder with no asset files, under 32-bit and 64-bit CLR hosts when available. It does not upload to GitHub. Full UI testing is currently on Windows 10 22H2 x64; other systems remain unverified. The user reports normal resource usage and no stutter after approximately 2.5 hours.

To record an hour of usage from a running instance:

```powershell
.\measure-usage.ps1 -DurationMinutes 60 -IntervalSeconds 10
```

With multiple instances, supply `-ProcessId`. CSV includes private and total working sets, private bytes, CPU deltas, and GDI/USER handles. The sampler runs only when invoked.

Run `.\test.ps1` for the upstream parity, rope, rigid-body, and window-behavior smoke tests. The window test also writes still and moving pet previews to `.test-output`. If Node.js is installed, the unchanged upstream JavaScript is checked against the reference fixture; Node.js is not required to build or run WindowPet.

## macOS

A native Swift/AppKit macOS adaptation is available under [`macos/`](macos/README.md). Build with `./macos/build.sh`, then open `dist/macos/Window Pet.app`. It includes a permission-free demo window, four corners and rope lengths, the existing image pet, poking and stowing. The Mac model uses ten independently simulated rope segments, filtered window acceleration, and tuned damping to retain cord bending and rebound while reducing micro-drag amplification; the original 12-segment solver remains as a test reference. The macOS v0.0.2 release supports Apple Silicon on macOS 12 or later; see the macOS README for validation and remaining compatibility limits.

## Implementation

- `SettingsForm` lists visible top-level windows by HWND and offers the three settings.
- `PetForm` is a transparent, mouse-transparent drawing window. Its location is derived directly from the selected window's `GetWindowRect`. The anchor is rendered at a fixed pixel inside this overlay.
- `HitForm` provides two tiny, near-invisible elliptical input regions: one following the pet body for pokes, and one fixed at the anchor for stowing and restoring. The rest of the drawing canvas passes mouse input to the application underneath.
- `VerletRopeSolver` ports the integration and symmetric quarter-distance correction from `code4fukui/physics-rope` (MIT). The core is verified against 450 node positions generated by the unchanged original JavaScript. It uses double precision and time-scaled damping, with no frame allocations. The native adapter stops constraint iteration once segment errors are below 0.004 px; its higher iteration budget is only needed for abrupt movements.
- `RopePhysics` adapts that core to 12 segments and a fixed 120 Hz step. Only the anchor changes position in simulation world space when the window moves. Rope nodes receive zero gravity, while the free pet endpoint has gravity and ten times one rope node's inertial mass. Damping is relative to window translation, preventing constant-speed dragging from continually bowing the cord. Native bounds on relative speed and inward pendant rebound control abrupt impulses. A subpixel symmetry seed allows perfectly vertical slack to bend without adding rope gravity. Stowed mode runs no rope physics.
- `PetBodyPhysics` treats the rope endpoint as the pet's top pivot. It scans the rendered image alpha once at attachment time to estimate center of mass and moment of inertia. Gravity and the rope endpoint's filtered acceleration produce angular motion, with light damping bringing the center of mass below the pivot when movement ends. The pet rotates around its attachment point; stowed mode resets this motion.
- Target location events (`SetWinEventHook`) immediately synchronize the overlay and anchor input region on the UI thread. The idle timer remains a fallback, rather than the sole mechanism for following a moving window.
- Rope rendering uses a smooth cubic path with rounded ends and a fine inner highlight. `LayeredSurface` presents premultiplied pixel alpha, avoiding color-key fringes. One 600 × 440 bitmap and native drawing context are reused for the attachment lifetime and disposed on close.
- The 600 × 440 overlay reserves space for maximum rope length, swing, and the larger image pet. Initial placement happens before the first paint, avoiding the startup flash at the edge.
- The drawing layer and two small input regions remain attached to the target's normal window order, so other windows cover them. None takes focus. The app polls at 16 ms while moving and 66 ms at rest, and repaints only on changes. The selected image asset is decoded once; no browser or JavaScript engine is loaded.

Window stacking is synchronized on each tick, so a newly raised window can briefly expose the pet for at most one idle tick (66 ms). Event-driven z-order updates and multi-window attachments are later architecture steps. The three pets are original placeholder drawings.

## Relevant open source

- [electron-overlay-window](https://github.com/SnosMe/electron-overlay-window): target discovery and overlay following (MIT); its single-overlay model is less suitable for future multi-window support.
- [ImOverlay-DX11](https://github.com/rabbanyhmm/ImOverlay-DX11): native multi-window transparent rendering and click-through patterns.
- [procmod/overlay](https://github.com/procmod/overlay): Rust/Direct3D target-following overlay; its input is fully click-through.
- [physics-rope](https://github.com/code4fukui/physics-rope): MIT source used for the current C# integration and constraint core. Its demo fixes both ends; our adapter uses a fixed window anchor and a free pendant end. Original sources and attribution are under `third_party/physics-rope` for verification.
- [Unity-Verlet-Rope](https://github.com/jongallant/Unity-Verlet-Rope): MIT reference evaluated for an earlier rope prototype.

See [repo evaluation](REPOSITORY_EVALUATION.md) for local clones and validation results.
